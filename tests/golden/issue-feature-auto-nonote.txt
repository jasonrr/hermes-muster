## How to work

1. Bug: reproduce it first, then find the root cause before any edit. Trace the bad value back to its source, instrument component boundaries, diff against the nearest working example. One stated hypothesis at a time (smallest probe, undo it if wrong, never stack fixes). After 3 failed fixes, stop and ask the human.
2. Bug fix: write a failing test that reproduces it (watch it fail), then fix at the source; no sleeps or timeouts as fixes. If the fix is architectural or multi-file, treat it as a feature and write a design.
3. Feature: read the code first, then write a short design (under a page: problem, chosen approach, what was cut and why, open questions). Ask one question at a time, with options. Propose 2–3 approaches when there is a real choice. For UI, show an ASCII mockup with realistic data.
4. Cut test on every element: "what breaks if we don't build this?" No concrete answer → cut it and say so. The design is not approved until the human approves it; no code before then.
5. Then a plan a zero-context agent could execute, written to `docs/plans/YYYY-MM-DD-<slug>.md` in this worktree and committed with the work: cite the nearest existing in-repo pattern per area (read docs/learnings.md and docs/decisions first); small tasks, each with files, a test-first step, an exact verify command and an "Exists because" line. No "TBD" or "similar to task 2".
6. Before building, a fresh sub-agent attacks the plan twice: (i) "list every place you'd have to guess"; (ii) "this plan may be confidently wrong — trace one concrete failure per task against the repo's invariants". Fix every finding. That is the plan's approval: the human approves the design, not the plan; never ask them to.
7. Build task by task on the branch, never main: recheck each task's "Exists because" against current code. Tests first, minimal code, lint and types clean, no dead code, match surrounding style. Commit with explicit paths (never `git add -A`, never a bare `git stash`). Verify output yourself; a sub-agent's report is a claim, not evidence. After each task, a fresh cheap sub-agent reviews that task's diff against its brief and the lenses in docs/review-lenses.md if the repo has one (default: correctness, invariants); fix its p1s before the next task. Stop and ask if the code contradicts the plan, verification fails twice, or you need files outside the task.
8. Before opening the PR, a fresh sub-agent attacks the live tree and the diff, using docs/review-lenses.md if the repo has one (default lenses: correctness, invariants, evidence = claims vs what tests assert, simplicity capped at p2). It must run the tests, exercise the changed surface, and trace callers of changed functions. Each finding is a concrete failure (input/state → wrong behavior, file:line, severity). Zero findings needs a probe log.
9. Severity: p1 = data loss, invariant or security violation, mainline breakage (blocks the PR). p2 = real edge, missing I/O error handling, silent failure. p3 = hygiene. ## Production and activation

No production note for this repository: nothing says what a merge deploys. Do not assume; if the work depends on it, ask the human.

A merge is not activation. Someone still has to make the change live, so your pull request body carries an
`## Activation` section that tells them how. Put it immediately before the final `Closes #n` line (which stays
last), or at the end of the body when there is none. Muster carries it to the human after the merge.

- **Merge triggers:** what merging does in this repository, citing the note above or the repository's own docs
  (a deploy workflow, an install or update guide), or "unknown: nothing says".
- **Steps:** in order, every command and every change outside this pull request: settings in a config file outside
  the repository, scripts to copy, migrations, restarts. Give a config change as the exact text to add and where.
  Name a secret; never write its value.
- **Who:** who runs each step, and what approval it still needs. Merging authorizes none of them.
- **Verify live:** a command, its expected output, and what it proves. Mark each step and check tested (you ran it
  here) or untested.
- **Rollback:** how to undo the activation.

When the merge alone is the whole change and there is nothing to run or check (documentation or tests only), write
"Nothing to activate:" and why instead.

Never run a step yourself: no install, deploy, restart, migration, or write to configuration outside this worktree.
