## The seams (decided here; every task relies on them)

Two plan attacks found the design's module map one module short. Telegram's moved code and Slack's new code both
need helpers that live in `gateway.py` today, and a channel must not import `gateway`. The design keeps its
architecture and gains one module:

- **`muster/channels/shared.py`**: the neutral helpers both channels and the gateway import.
  - `CTX`, set by the plugin's `register()`.
  - `BOOT`; `log(line)` (logs as "gateway"); `ensure_config()`; `soon(loop, coro)`; `session(rid, n)`.
  - The text builders:
    - `title(req)`.
    - `render(req, n, *, cap, label_max, tail)`. `tail` is the channel's hint lines: Telegram's are today's
      text; Slack's are "Pick one, or type your own answer below." and, for multi, "Tick any, then Submit".
    - `buttons(req, n, *, label_max, number_multi)`. Telegram passes `number_multi=True`, because its typed
      answer names numbers. Slack passes False, because checkboxes carry their own index.
  - The lifecycle guards both channels use: `LIVE`, `SCAN_EVERY`, `CHECK_EVERY`, `CLOSED_EVERY`, `RETRY_MAX`,
    `now`/`clock`, `checked` (dict), `archived(ledger)`, `retire(ledger)`, `stale_requests(ledger)` and
    `backoff(ref, why)`, all moved verbatim from gateway.py.
  - The hub: `answer` and `permission`. The gateway assigns them in `gateway.setup`, and channels call
    `shared.answer(rid, n, value)` and `shared.permission(rid, answer)`.
    - `answer` returns `(req, result, part)`, where `result` is `decisions.answer_part`'s: `"accepted"`,
      `"completed"`, `"duplicate"` or `"closed"`.
    - `permission` returns `(req, ok)`.
  - `slack_text(s)`: escapes `&`, `<` and `>` for Slack mrkdwn. Every agent- or human-written string a Slack block
    shows goes through it (review F6).
- **The Protocol** (`channels/__init__.py`, docstring only; this replaces design §4's list):
  - `name`, `durable_prompts`.
  - `register(ctx)`: wires Hermes; returns False when this Hermes lacks the surfaces.
  - `validate(settings) -> list[str]`; `home() -> str`, the chat used when `notify_chat_id` is empty.
  - `async destination(req) -> (ready, meta)`.
  - `async present(req, meta, questions) -> Sent`: posts only the question indexes given.
  - `async present_approval(req, meta) -> Sent`; `Sent = {"messages": {str(n): [new ids]}, "failure": str|None}`.
  - `async outcome(req) -> bool`: edits every message of an ended request to `req["outcome"]`, loop included.
  - `release(rid)`; `release_ended(live: dict)`; `track(req)`: binds saved message ids in memory.
  - `async reply(event) -> dict|None`; `async steps()`: one lifecycle pass over conversations.
  - Design §4's `ready()` is dropped. Its one caller, `events.muster_pages`, runs in the hook process, where
    `decisions.gateway_up()` already answers it.
- **The gateway** keeps:
  - `S` (`loop, task, configured, recovered, presenting, retry, watch, edit_failed, swept, vetted`).
  - `scan`, `handle`, `presented`, `answered`, `record`, `shape`, `compose`, `on_answered`, `background`,
    `on_dispatch` and `setup`.
  - `handle` does: stale check → `CHANNEL.release` → reconcile → **skip rule** → vetted → `destination` →
    status re-read (not `open` → return) → present → `presented(rid, old ∪ new ids, failure)`.
- **The skip rule** (p1 from the attack, made per kind by the review):
  - A request is not presented when `presented.boot == BOOT`.
  - On a `durable_prompts` channel it is also not presented when it is fully shown. Define
    `slots(req) = ["0"]` for `permission`, else `[str(n) for n in range(len(req["questions"]))]`. Fully shown means
    every slot has a non-empty id list in `presented.messages` (a failed send can leave `"1": []`), and
    `presented.platform` equals `CHANNEL.name`. `presented()` writes `platform`, so a platform switch re-presents
    open requests instead of trusting the other platform's ids.
  - Such a channel is asked to `present` only the question slots with no saved id; a failed partial send retries
    only those. A permission with no saved id is presented whole.
  - `presented()` writes Superseded edits only when `not CHANNEL.durable_prompts`.
  - On a `durable_prompts` channel only, `handle` runs the build/feedback `vetted` check (`decisions.obsolete`)
    *before* the skip rule. A durable Merge button whose pull request moved on is then staled, and its buttons
    are removed by `outcome`. Telegram's order is unchanged.
- **Approvers** (fixes the Telegram DM regression): `core.approvers()` returns the non-blank entries of
  `notify_user_id`, read as a comma-separated string ("42,43"). A YAML list or an int is accepted too. The
  string form keeps the setting `type: str`, which Hermes's settings writer accepts (review F9).
  - When none are set it returns `[notify_target()["user_id"]]`: the DM chat in DM mode, as today.
  - The one exception: a group (`notify_chat_id` set) with no `notify_user_id` returns `[]`, so nobody is
    authorized, as today.
  - `notify_target()["user_id"]` is the first configured approver, else today's `notify_chat_id` or DM fallback,
    unchanged.

## Task 1: `decisions.answer_part` (durable partial answers)

**Files:** `muster/decisions.py`, `tests/test_decisions.py`.

**Exists because:** design §9 says a Slack request's partial answers must survive a restart.

**Pattern:** `decisions.transition` (decisions.py `transition`: one flock; `req.update(fields, status=to)`; one
`audit` entry `{at, step, result}`; `save`).

**Test first.** Use `compose = lambda parts: {"p": parts}` and a two-question request
(`decisions.create("question", "led1", questions=[q, q], choices=[["A", "B"], ["A", "B"]])`).
It returns `(req, result)`, where `result` is one of `"accepted"`, `"completed"`, `"duplicate"` or `"closed"`. A
plain bool could not tell a fresh non-final answer from a repeat (review F2).
- `answer_part(rid, 0, ["A", [0]], 2, compose)` returns `"accepted"`. The file has `partial == {"0": ["A", [0]]}`
  and status `open`. Audit gains `{"step": "part", "result": "0"}`.
- Then `answer_part(rid, 1, ["free", None], 2, compose)` returns `"completed"`, status `answered`,
  `answer == {"p": [["A", [0]], ["free", None]]}`, and an audit step `answered`.
- Question 0 again while open returns `"duplicate"` and leaves the part unchanged: the first answer wins.
- A request that is not `open` (transitioned to `stale`; `load` reads the archive) returns `"closed"` and writes
  nothing.
- Two threads behind a `threading.Barrier` answer q0 and q1. Exactly one gets `"completed"`, and both parts are
  saved.

**Code:** `answer_part(rid, n, part, total, compose)` under `locked(rid)`:
1. Load. If the status is not `open`, return `(req, "closed")`. If `str(n)` is already in `partial`, return
   `(req, "duplicate")`.
2. Set `partial[str(n)] = list(part)` and append the audit entry.
3. When `len(partial) == total`: `req.update(answer=compose([partial[str(i)] for i in range(total)]),
   status="answered")` and append the `answered` audit entry.
4. `save`, then return `"completed"` or `"accepted"`.

**Verify:** `.venv/bin/python -m pytest -q tests/test_decisions.py`.

  - `muster_submit` with `state.values[block]["muster_multi"].selected_options` of `["0", "2"]` → the JSON list
    of those labels.
  - Submit with none ticked → ephemeral "Tick at least one".
- Each of these is refused with one `chat_postEphemeral(channel, user, text="Not authorized")` and no answer:
  - a non-approver;
  - another channel;
  - an unknown `block_id`, or a `block_id` whose rid has no request;
  - an exception inside the check (fail closed).
- No thread check and no workspace check (review F8/F17, cut test). Only the bot posts muster blocks, and only
  where `destination` put them, so the `block_id` already binds the tap to its request. Slack has no "resent to
  General" path, which is what Telegram's topic check exists for. User ids are unique across workspaces, so the
  approver check bounds Slack Connect channels. A thread check would turn an unverified payload field
  (`container.thread_ts`) into a total outage if its shape differs. This cuts the design's
  `notify_workspace_id`: a deviation from design §5/§6, to be named in the PR.
- Double tap / redelivered body: the second gets ephemeral "Already answered: <part>", and there is one answer.
- Race: two approvers tap different choices on q0 concurrently. `answer_part` keeps the first, and *both* messages'
  updates show the stored part (from `shared.answer`'s return), never the losing tap.
- Restart: `slack.T = slack.State()` and the same files. Tap q1 of a request whose q0 was answered before: the
  request is `answered` with both parts.
- A retired run (conversation `deleted`, request `stale`): ephemeral with the outcome, no answer.
- Two runs in two threads, with the same question text: each tap answers its own request only.

**Code:**
- `on_action(ack, body, action)`: `await ack()`, then `shared.CTX.spawn_task(handle(body, action))`.
- `handle`:
  1. Parse `block_id` (`mu:<rid>:<n|approval|deny>:<kind>`).
  2. Authorize: `channel.id` == `notify_chat_id` and the user in `core.approvers()`. This runs before any request
     is read, so nothing about the request leaks to a refused user.
  3. Load the request (missing → refused as unknown). Not `open` → ephemeral with the outcome or status.
  4. For a question: `req, result, part = await shared.answer(rid, n, value)`. On `"accepted"` or `"completed"`,
     `chat_update` the question message with `part`. On `"duplicate"`, ephemeral "Already answered: <part>" and
     `chat_update` with the stored part. On `"closed"`, ephemeral with the outcome.
