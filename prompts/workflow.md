# How to work

1. Bug: reproduce it first, then find the root cause before any edit. Trace the bad value back to its source, instrument component boundaries, diff against the nearest working example. One stated hypothesis at a time (smallest probe, undo it if wrong, never stack fixes). After 3 failed fixes, stop and ask the human.
2. Bug fix: write a failing test that reproduces it (watch it fail), then fix at the source; no sleeps or timeouts as fixes. If the fix is architectural or multi-file, treat it as a feature and write a design.
3. Feature: read the code first, then write a short design (under a page: problem, chosen approach, what was cut and why, open questions). Ask one question at a time, with options. Propose 2–3 approaches when there is a real choice. For UI, show an ASCII mockup with realistic data.
4. Cut test on every element: "what breaks if we don't build this?" No concrete answer → cut it and say so. The design is not approved until the human approves it; no code before then.
5. Then a plan a zero-context agent could execute: cite the nearest existing in-repo pattern per area (read docs/learnings.md and docs/decisions first); small tasks, each with files, a test-first step, an exact verify command and an "Exists because" line. No "TBD" or "similar to task 2".
6. Before building, a fresh sub-agent attacks the plan twice: (i) "list every place you'd have to guess"; (ii) "this plan may be confidently wrong — trace one concrete failure per task against the repo's invariants". Fix every finding.
7. Build task by task on the branch, never main: recheck each task's "Exists because" against current code. Tests first, minimal code, lint and types clean, no dead code, match surrounding style. Commit with explicit paths (never `git add -A`, never a bare `git stash`). Verify output yourself; a sub-agent's report is a claim, not evidence. Stop and ask if the code contradicts the plan, verification fails twice, or you need files outside the task.
8. Before opening the PR, a fresh sub-agent attacks the live tree and the diff, using docs/review-lenses.md if the repo has one (default lenses: correctness, invariants, evidence = claims vs what tests assert, simplicity capped at p2). It must run the tests, exercise the changed surface, and trace callers of changed functions. Each finding is a concrete failure (input/state → wrong behavior, file:line, severity). Zero findings needs a probe log.
9. Severity: p1 = data loss, invariant or security violation, mainline breakage (blocks the PR). p2 = real edge, missing I/O error handling, silent failure. p3 = hygiene. Mark each CONFIRMED (reproduced) or PLAUSIBLE (couldn't refute). Drop one only by proving it wrong. Max 3 fix rounds per issue, then decide or ask. Fix all p1s in one pass and re-review that fix. List p2/p3 in the PR body.
10. Run the full tests and lint fresh and read the output before saying done. In the PR, record anything that deviated from the plan; add one `pattern → consequence` bullet to docs/learnings.md for any surprise.
11. One PR, body ends `Closes #n`. Never merge, approve, deploy, force-push, push to main, or edit `.github/`, CI, deployment config, secrets, lockfiles or agent-instruction files. Wait for the human's call.
12. Ask the human when unsure; never guess. Trivial one-file changes skip the design and plan steps.
13. Sub-agents get a model per job: cheap for transcription and broad scans, the default for most work, the top model only for architecture. Never let a sub-agent inherit the top model by default. Give each one a self-contained brief (no session history). One implementer at a time on this tree.
